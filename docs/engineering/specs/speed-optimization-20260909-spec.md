## Problem Statement

当前无法从现有日志可靠判断企业微信 Agent 请求是否普遍变慢，也无法将端到端尾部延迟归因到敏感预检、媒体处理、MCP 加载、Pi 模型轮次、工具调用、回复队列或最终发送。现有日志缺少统一 request-scoped 关联、阶段覆盖和一致的终止状态；在缺少真实样本时直接调整模型、MCP 或 Pi 工具循环会引入不可验证的行为变化。

## Solution

先在不改变业务行为的前提下，补充 request-scoped 阶段耗时观测。每个被采样的请求输出一条结构化 JSON 汇总，使用单调时钟记录整数毫秒，覆盖关键阶段、速度分类、终止状态和固定错误分类。正常请求按 10% 采样，错误、超时、取消、TTL 暂停以及较慢请求强制记录。生产环境使用脱敏字段；仅临时隔离非生产环境在显式开关严格等于 `true` 时允许受控原文调试。采集真实样本后，按请求类型、终态、模型和工具计算 n、p50、p95、p99，再决定后续优化。

## User Stories

1. 作为维护者，我希望每个被采样请求有随机 request ID，以便关联同一请求的各阶段数据而不暴露会话标识。
2. 作为维护者，我希望看到请求总耗时，以便判断端到端延迟分布。
3. 作为维护者，我希望看到敏感请求预检耗时，以便判断前置模型判断是否造成显著等待。
4. 作为维护者，我希望看到媒体处理耗时，以便区分媒体解析造成的延迟。
5. 作为维护者，我希望看到 MCP 加载耗时，以便判断连接、加载或缓存是否造成等待。
6. 作为维护者，我希望看到 Pi 模型轮次耗时，以便区分模型响应与其他阶段。
7. 作为维护者，我希望看到每次工具调用耗时及安全工具标识，以便定位工具侧尾部延迟。
8. 作为维护者，我希望看到回复队列等待和 drain 耗时，以便判断流式排队是否成为瓶颈。
9. 作为维护者，我希望看到最终发送耗时，以便区分业务计算与企业微信网络发送。
10. 作为维护者，我希望看到 bot 和模型名称，以便按运行配置比较耗时分布。
11. 作为维护者，我希望看到请求包含的轮次信息，以便按单轮、多轮请求分层统计。
12. 作为维护者，我希望正常请求只按 10% 采样，以便控制日志量。
13. 作为维护者，我希望错误、超时、取消和 TTL 暂停请求始终记录，以便异常问题不会因采样丢失。
14. 作为维护者，我希望五分钟及以上请求被标记为 `slow`，以便识别较慢请求。
15. 作为维护者，我希望十分钟及以上请求被标记为 `very_slow`，以便识别特慢请求。
16. 作为维护者，我希望速度分类只影响观测和采样，不影响 Pi 循环、提前中断、降级或最终回复。
17. 作为维护者，我希望尚未完成的阶段记录为 `null`，以便区分零耗时与未执行或未完成。
18. 作为维护者，我希望每条指标包含统一 `terminal_status`，以便区分完成、错误、取消和 TTL 过期。
19. 作为维护者，我希望错误使用固定错误分类，以便统计失败原因而不泄露完整错误内容。
20. 作为安全负责人，我希望生产指标不包含用户正文、个人信息、会话 key、凭据、完整错误、工具参数或工具返回内容。
21. 作为非生产排障人员，我希望在临时隔离环境通过独立环境变量显式开启原文调试，以便复现问题。
22. 作为非生产排障人员，我希望原文错误和工具数据带固定标签并受长度上限约束，以便既能排障又避免日志无限膨胀。
23. 作为非生产排障人员，我希望序列化失败使用固定占位文本并继续记录，以便观测失败不影响业务请求。
24. 作为运维人员，我希望原文调试沿用现有日志系统的权限和保留策略，以便不引入第二套日志生命周期。
25. 作为系统维护者，我希望指标采集失败不影响业务响应，以便观测能力不会降低服务可用性。
26. 作为系统维护者，我希望接入指标后 Pi 仍只有真实 `agent_end` 且 `stopReason === "stop"` 的文本才作为正常最终回复，以便观测改动不改变生命周期语义。
27. 作为系统维护者，我希望接入指标后不恢复旧 Planner、预检索、审核、runtime Todo、direct-evidence 或绕过 Pi 的模型调用，以便性能调查不会引入旧外围控制。
28. 作为维护者，我希望能按正常、工具调用、多轮、超时和取消等分层计算 n、p50、p95、p99，以便依据真实数据而非猜测优化。
29. 作为维护者，我希望能按模型、工具和轮次归因尾部延迟，以便只优化已被数据证明的瓶颈。
30. 作为产品负责人，我希望优化前后可比较同类请求的 p95 和错误率，以便验证优化是否真正改善体验。

## Implementation Decisions

- 采用 request-scoped 单条结构化 JSON 汇总日志，而不是为每个阶段单独输出不可关联的日志。
- 使用单调时钟计算阶段差值，结果为非负整数毫秒；未完成阶段使用 `null`。
- 指标至少包含随机 request ID、bot 名称、模型名、工具安全标识、总耗时、敏感预检、媒体处理、MCP 加载、Pi 模型轮次、工具调用、回复队列、最终发送、速度分类、轮次、`terminal_status` 和固定错误分类。
- 正常请求采样率为 10%；错误、超时、取消、TTL 暂停以及 `slow`/`very_slow` 请求强制记录。
- 速度边界采用左闭区间：小于 5 分钟为 `normal`，大于等于 5 分钟且小于 10 分钟为 `slow`，大于等于 10 分钟为 `very_slow`。
- 速度分类只用于采样和分析，不参与业务控制。
- 生产脱敏依赖部署配置保证原文调试关闭；本规格不新增应用层生产环境自动忽略或构造层强制过滤机制。
- 非生产原文调试仅用于临时隔离环境，通过单一独立环境变量显式开启，且只有严格等于 `true` 才开启；默认关闭。
- 非生产原文沿用现有日志系统，保留基础脱敏字段，并将受控原文以固定标签追加到普通文本字段，不新增 `debug` 字段。
- 错误、工具参数和工具返回内容均设置固定长度上限；无法安全序列化时使用固定占位文本。
- 指标写入失败必须被隔离，不得改变业务请求结果。
- 指标接入点复用现有请求生命周期阶段，不恢复宿主对 Pi 生命周期、工具总次数、递归次数或最终完成条件的控制。
- 先采集真实样本，再按请求分层计算 n、p50、p95、p99；数据不足前不并行化 MCP、不更换模型、不调整工具循环或回复链路。

## Testing Decisions

- 测试只验证外部可观察行为：指标字段、阶段值、采样结果、安全边界、终止状态和业务结果不变；不锁定内部计时器实现或私有函数结构。
- request-scoped 指标测试覆盖正常请求、慢请求、特慢请求、错误、超时、取消、TTL 暂停、未完成阶段和记录失败。
- 边界测试覆盖总耗时恰为 5 分钟和 10 分钟，以及阶段未结束时的 `null`。
- 采样测试验证正常请求 10% 采样，同时验证异常和慢请求强制记录。
- 安全测试验证生产脱敏、非生产开关关闭、非严格 `true`、原文长度限制、固定标签和序列化失败占位文本。
- 请求主流程回归测试验证 Pi 生命周期、工具调用、TTL 行为和正常最终回复门槛不变。
- 测试优先复用现有配置、流式 TTL、Pi runtime 和 adapter 测试接缝；新增接缝仅限 request-scoped 指标汇总所必需的最高层接口。
- 通过 `npx tsc --noEmit` 和 `npm test` 验证；采集部署样本后再进行真实数据分位统计。

## Out of Scope

- 本规格不直接优化任何已存在的模型、MCP server、工具实现、缓存策略或回复网络链路。
- 不恢复或新增 Planner、预检索、审核、业务回答重写、recovery synthesis、runtime Todo、direct-evidence 或 `baseModel.invoke` 路径。
- 不使用耗时分类控制 Pi 循环、工具预算、提前中断、降级或最终回复。
- 不记录生产环境用户正文、个人信息、会话 key、API key、完整错误原文、完整工具参数或完整工具返回内容。
- 不建立新的外部日志平台、任务平台或指标数据库。
- 不在缺少真实样本时断言具体瓶颈或执行性能改造。

## Further Notes

当前工作区没有足够近期真实日志样本，无法证明请求普遍变慢，也无法计算可靠的 p50、p95、p99。第一阶段成功标准是获得可归因、脱敏且不改变业务行为的真实观测数据；后续优化必须以分层样本为依据。生产原文安全性依赖部署配置纪律，因此部署检查和权限、保留期限管理属于运行治理要求，不应通过扩大业务代码控制面来替代。
