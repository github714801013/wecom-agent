# Pi 智能体迁移与 MCP 插件化规格

## 问题陈述

当前 Agent 运行链路基于 LangGraph/LangChain，并叠加 Planner、预检索、自动验证、最终审核和业务重写等多层循环。一次请求可能重复进入模型和查询工具，造成响应时间过长、取消边界不清晰、工具状态分散以及企业微信流式回复适配复杂。项目需要改用 Pi 作为 Agent runtime，并将 MCP Skill 通过 Pi Plugin 接入，同时保留现有安全、会话、权限范围和企业微信回复契约。

## 解决方案

使用 Pi Agent 作为单次请求的有状态执行内核，通过 MCP Plugin 将现有 MCP 工具转换为 Pi AgentTool。宿主仅保留消息接收与去重、安全前置拦截、会话和权限范围、运行截止时间、工具预算、企业微信流式输出、最终输出门和持久化。

目标流程：

```text
RECEIVED → GUARDED → RUNNING（Pi Agent + MCP Plugin）→ FINALIZE → PERSIST → COMPLETED
```

异常状态分别进入 FAILED、CANCELLED 或 PAUSED；暂停恢复回到 RUNNING，不能重复执行已完成的工具调用。

## 用户故事

1. 作为企业微信用户，我希望问题由 Pi Agent 直接处理，以便减少无效的多层 Agent 循环。
2. 作为企业微信用户，我希望仍能获得流式进度和最终回答，以便了解请求是否仍在执行。
3. 作为企业微信用户，我希望工具查询超时或被取消时能尽快收到明确结果，而不是一直等待。
4. 作为企业微信用户，我希望查询结论继续保留 SQL、字段名、参数值、枚举值、错误码、状态码和接口路径的原样信息。
5. 作为企业微信用户，我希望业务模式继续使用易懂语言，开发模式继续允许原样技术回答。
6. 作为企业微信用户，我希望同一条消息不会因重试或流恢复而重复执行工具。
7. 作为企业微信用户，我希望流式连接过期后可以继续处理，而不是从头重新执行已完成的工具。
8. 作为企业微信用户，我希望明确要求清理会话时，历史记录和记忆可以被清理。
9. 作为系统管理员，我希望 MCP 工具继续受到白名单、黑名单、Header/Profile 和 Repo Scope 的约束。
10. 作为系统管理员，我希望 MCP 工具执行能够继承请求级取消信号和截止时间。
11. 作为系统管理员，我希望单个工具失败不会导致其他 MCP Server 的工具加载状态被错误覆盖。
12. 作为系统管理员，我希望 MCP Session 失效时最多按既定策略重建一次，避免无限重试。
13. 作为系统管理员，我希望 Pi 不自动启用具有文件系统或命令执行权限的默认编码工具。
14. 作为系统管理员，我希望工具调用次数、重复调用和查询调用次数受到运行时硬限制，而不是只依赖 Prompt。
15. 作为系统管理员，我希望工具结果过大时仍能通过摘要和分段读取机制控制模型上下文大小。
16. 作为系统管理员，我希望每次运行都能记录开始、工具执行、取消、失败和结束等关键阶段，便于定位慢点。
17. 作为开发者，我希望 Pi 事件能映射为稳定的文本增量、工具开始、工具更新、工具结束、完成、错误和取消事件。
18. 作为开发者，我希望模型使用当前 OpenAI-compatible endpoint、API key 和模型配置，不需要改动上游服务。
19. 作为开发者，我希望 Pi Agent 的业务 session 标识与现有租户会话键保持隔离，避免跨会话串数据。
20. 作为开发者，我希望现有安全预检发生在 Agent 和工具加载之前。
21. 作为开发者，我希望简单文本请求、单工具请求、多工具请求和工具预算耗尽请求都有可重复的自动化测试。
22. 作为运维人员，我希望容器运行时满足 Pi 版本要求，并能通过构建、启动和优雅停止验证。

## 实现决策

- 使用已核验的 Pi Agent Core 与 Pi AI 稳定版本；运行时采用 ESM，并将 Node 运行环境升级到满足该版本要求的版本。
- 以 Pi Agent runtime 作为新的底层执行边界；企业微信适配器消费统一的内部事件，不依赖 LangGraph 的消息元组和递归恢复协议。
- MCP Plugin 继续复用现有 MCP SDK 的 SSE/Streamable HTTP transport、连接缓存、Header/Profile、Repo Scope、白名单/黑名单和加载超时能力。
- 每个 MCP 工具转换为 Pi AgentTool。工具描述使用原 MCP 描述，参数使用可供 Pi 校验的 JSON Schema；执行结果统一转换为文本或图片内容和结构化 details。
- 工具执行必须支持 AbortSignal、单工具 timeout、请求总 deadline、工具调用预算、查询预算、重复调用限制和错误转换。所有限制在运行时执行，Prompt 仅作为辅助说明。
- Pi Agent 按请求创建；MCP 工具注册表和可复用的 MCP 客户端资源按进程复用。现有业务 sessionKey 不直接替换为 Pi sessionId。
- 不启用 Pi coding-agent 默认文件、命令或其他宽权限工具，只注册经过当前 MCP 配置筛选的显式工具。
- Pi 的生命周期事件映射为 `text_delta`、`tool_start`、`tool_update`、`tool_end`、`agent_end`、`error` 和 `aborted`；事件晚到时按请求结束标记丢弃。
- 请求总 deadline 由宿主创建 AbortController 和定时器驱动；结束时调用 Pi abort 并等待 idle，避免遗留工具执行和监听器。
- 最终输出采用单一 finalization gate，完成必要的完整性、安全和业务语言检查；不再启动独立自动验证 Agent 循环。
- 首期删除或合并 Planner、Search Prelude、Agentic RAG 和 LangGraph recursion recovery 对主请求的强制嵌套调用；需要核验时由当前 Pi turn 使用普通 MCP 工具完成。
- 会话仍由现有 SessionManager 管理，保存业务会话、回复模式、Header/Profile、Repo 提示、Human Loop 和恢复所需的最小工具完成信息。
- 依赖切换以真实类型声明、编译结果、文本/工具/流式 smoke 和真实 MCP smoke 为准；在这些验证通过前，不删除仍被视觉分析、消息类型或 MCP 适配使用的 LangChain 依赖。

## 测试决策

- 测试只验证外部行为和稳定契约，不绑定 Pi 内部私有字段或事件实现细节。
- 验证 MCP 工具描述、参数 Schema、执行结果转换、Header/Profile、Repo Scope、白名单/黑名单和拒绝行为。
- 验证工具单次超时、请求总 deadline、AbortSignal 取消、迟到事件丢弃、重复调用和预算耗尽。
- 验证文本增量、工具生命周期事件、错误和取消事件到企业微信内部事件的顺序及内容。
- 验证无工具纯文本、单工具、多工具、MCP Session 失效、暂停恢复和同一会话连续请求。
- 验证敏感凭据前置拦截发生在工具加载之前，且业务字段和 URL 参数不会仅因字段名被误拦截。
- 验证最终输出仍保留事实值，业务模式不输出代码，开发模式不发生不必要裁剪。
- 以现有独立 TypeScript 测试脚本和 TypeScript 编译作为优先测试方式；补充 MCP、Pi Agent、WeCom contract 和 Docker smoke。
- 测试必须记录命令、退出码、跳过项和无法连接外部服务的原因；外部服务不可用不能伪装成通过。

## 范围外

- 不在本规格中重做企业微信 WebSocket 协议、卡片协议或媒体下载协议。
- 不把 Pi CLI/RPC 子进程作为首期运行边界。
- 不直接采用 Pi 默认 JSONL session 作为业务会话数据库。
- 不引入新的持久化数据库或分布式队列。
- 不为所有 MCP Server 自动开放写入、删除或命令执行能力。
- 不在没有兼容性证据的情况下删除视觉分析仍需要的 LangChain 依赖。
- 不在本首期同时实现跨进程分布式去重、完整沙箱系统或副作用工具的业务幂等补偿。

## 进一步说明

Pi 0.85.0 的运行环境要求 Node.js 22.19.0 或更高版本；项目容器基于 Node 22 镜像。Pi 核心不内置 MCP 和统一 timeout，因此 MCP transport、工具权限、取消、deadline 和审计仍由宿主负责。首期目标是完成可验证的 runtime 和 plugin 迁移，再逐步清理旧流程代码；不得因“已安装 Pi”而跳过真实模型和 MCP smoke。
