# timeout-recovery 缺陷诊断记录

## Phase 1 — 反馈环（已建立并运行，红灯）

运行命令：

```
node --loader ts-node/esm .scratch/timeout-recovery/loop-deadline-terminal.ts
```

实际输出：

```
[loop] elapsedMs=35 events=[]
AssertionError [ERR_ASSERTION]: 截止到达后既没有 agent_end，也没有任何可识别的终止事件
```

- 驱动路径：`createPiAgentFacade().streamPiEvents(prompt, { deadlineMs: 30 })`，假 Agent 只执行工具、永不发出 `agent_end`。
- 红灯断言：截止触发后流内必须出现可识别终止事件（`agent_end` / `aborted` / `error`）。
- 紧密度：35–44ms、确定性、无需人工介入、断言的是用户症状（拿不到任何可用于回复的终态）。

## Phase 2 — 复现与最小化

最小复现由三个负载要素构成，逐个移除任一要素都会转绿：

1. 一个永不自行结束的 Pi 执行（模型持续 `toolUse`）；
2. 截止触发 `abort()`；
3. 结束后没有 `agent_end`。

对应到线上：7 次失败请求 `piModelRoundMs` 均约 480004ms，`stopReason` 分布为 `toolUse` 377 / `stop` 5，说明第 1、3 个要素在真实流量中同时成立。

## Phase 3 — 假设排序（可falsify）

| 排序 | 假设 | 预测 |
| :--- | :--- | :--- |
| H1 | 模型无从得知已用时间：唯一时间约束是静态提示词句子，运行期不注入任何时钟事实 | 若周期性注入"已用/剩余时间"并在不足时要求收尾，轮次下降且能在截止前产出 stop 文本；不注入则维持 30–50 轮 |
| H2 | 收敛规则被穷尽规则压制：`business-prompt.md:371/374` 要求提问前穷尽路径，`business-base-prompt.md:10` 同义 | 若把穷尽规则限定为仅 Human Loop 前置条件、并把"证据闭合即回答"提为最高优先级，轮次下降 |
| H3 | 单轮成本过高：每轮中位 10.0s、p90 22.0s | 若单轮降到约 5s，同等轮次可压入预算；但换模型/压缩上下文才有此效果 |
| H4 | 分页读取制造额外轮次：`tool_result_file_read` 77 次 | 若减少落盘或首轮给出更完整证据，轮次下降约 10–13% |
| H5 | 追问重跑：同一问题被重复问 2–3 次，每次完整 8 分钟 | 若"继续"复用已完成节点，重复轮次消失（跨请求，不解释单请求不收敛） |

对 H3 的反证：单轮耗时**不随轮次增长**（0–9 轮 11.4s，40+ 轮 9.5s），因此上下文膨胀不是主因；H3 只能解释"同样的轮次更慢"，不能解释"轮次过多"。
对 H4 的量化：77 / 577 ≈ 13%，是因素但不是主因。
对 H5 的量化：请求内工具调用几乎不重复，重复发生在跨请求层面。

## Phase 4 — 已收集的判别证据

- `business-base-prompt.md:32` 已要求"证据不足且接近流式截止时，输出已确认内容和最小未确认项"，但运行期不提供任何"接近截止"的事实 → 该规则不可执行（支持 H1）。
- 三档时间口径不一致：提示词约 4–5 分钟、代码 `requestTimeoutMs` 480 秒、企微流安全 TTL 9 分钟。
- 线上探索在最后一轮仍在开启新战线（第 32–33 轮仍在调用 `query`/`code_snippet`/`impact`），未见任何收敛迹象（支持 H1/H2）。
- 超时被归类为 `errorCategory=pi_agent_end_stop_text_missing`，与"模型没有产出文本"不可区分，指标层面掩盖了真因。

## 结论

缺陷由两个面构成：

- **面 A（无终态）**：截止中止时不产生任何终止事件，消费方既拿不到内容也无法区分超时；这直接导致"拿不到结果"且错误分类具有误导性。
- **面 B（无收敛信号）**：运行期不给模型任何时钟事实，提示词中"接近截止就收尾"的规则不可执行；同时穷尽类规则持续推动检索。

两面需同时处理：只做 A 会把"无回答"变成"更早的无回答"；只做 B 仍会在个别长问题上无终态。

## 待用户决策

超时降级回答是否允许使用非 `agent_end(stop)` 的内容（历史轮次中已产生的非空 assistant 文本），或只接受"明确超时提示 + 已确认要点"。该决策决定面 A 的实现方式。

## 实施结果（implement 阶段回写）

采用的修复同时覆盖两面：

- **面 B（收敛信号）**：`src/pi-agent-runtime.ts` 新增 `PiRunBudget`，由 `createPiAgentFacade` 在每个流启动时绑定 `runStartedAt` 与 `deadlineMs`；`createPiMcpPluginTools` 在**每次工具结果的返回边界**追加 `[时间预算] 已用 Xs / 上限 Ys，剩余 Zs`，剩余不足 90 秒时追加"必须立即用现有证据给出最终结论，不要再发起新的检索"。注入点选在工具结果边界，因为它正是模型决定是否继续检索的位置。
- **面 A（无终态）**：`src/wecom-adapter.ts` 累计流式 assistant 文本（上限 40000 字符，取尾部），并在 `!piAgentEnded` 且已到达时间上限时发送"已确认要点 + 超时标注"，同时持久化会话；指标分类为 `terminalStatus=ttl_expired`、`errorCategory=pi_request_timeout`，与"模型没有产出文本"区分开。

提示词随之下调：`business-base-prompt.md` 删除与代码不一致的固定"4 分钟/第 5 分钟"口径，改为以运行时 `[时间预算]` 为准。

**被证实的假设**：H1（运行期不提供时钟事实，使"临近截止即收尾"不可执行）。H2（穷尽规则压制收敛规则）未被单独验证，因此保留为待观察项；提示词未做结构性重排。

**尚未验证**：模型收到剩余时间提示后是否真的提前收敛，需要在部署后用真实流量对比轮次分布（`turns`）与 `pi_request_timeout` 占比。

**刻意未做**（保留为后续可选）：未新增 Pi 终止事件类型（用已用时长推导即可判定超时）；未给"继续"实现跨请求的断点复用（属 H5，与本缺陷症状可分离）。

## 未确认项

- Pi SDK 在 `abort()` 后是否可能补发 `agent_end` 及其 stopReason 取值，需在实现阶段以真实 Agent 验证。
- 模型在收到"剩余时间不足"提示后是否确实收敛，需要部署后真实流量验证，不能由本地测试断言。
