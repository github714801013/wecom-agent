# 备用机押金支付回复完整性验证与修复计划

## 目标

使用真实问题“备用机 押金支付 支持哪些支付方式逻辑”验证服务是否会只返回阶段性进度，修复直到服务能输出完整业务结论。

## 关键假设

- 当前仓库是 Node/TypeScript 服务，证据为 `package.json`、`tsconfig.json`、`@wecom/aibot-node-sdk`、`@langchain/*`。
- 本次问题修复目标是智能助手回复完整性，不修改被查询业务项目代码。
- 已存在未提交的进度微动效改动，本轮保留并纳入测试、提交、部署。
- 如果远程企业微信真实消息不可直接模拟，则优先使用本项目诊断 HTTP 或新增最小诊断入口做服务级验证。

## 实施步骤

1. 检查现有诊断服务能力，确认是否能直接发起 agent 测试问题。
2. 用测试问题复现“不完整阶段性回复”或缺少完整结论的失败现象。
3. 定位问题发生在进度折叠、审核循环、最终回复覆盖、诊断入口还是 prompt 约束。
4. 最小化修复：优先调整最终回复完整性拦截和服务级测试入口，避免改动业务检索逻辑。
5. 增加或更新本地测试，覆盖阶段性回复不能作为最终答案、完整回复必须包含结论/依据/建议。
6. 执行 TypeScript 编译和相关测试。
7. 提交、推送、使用 Git Bash 部署。
8. 调用远程服务验证测试问题能得到完整回复。

## 验收标准

- 测试问题不会以“继续核实中”“继续读取”“准备输出结论”等阶段性文本作为最终回复。
- 最终回复至少包含：支持哪些支付方式、判断依据、入口/接口/项目中已核实的定位信息；证据不足时必须转 Human Loop，而不是停在进度句。
- 部署后远程服务健康检查通过，且验证接口返回完整内容。
