# 原始需求归档：wecom-dev-db-human-loop-suppression

日期：2026-06-24

## 用户原始需求

> /dev-spec-gen fetch("https://oa.dev.9ji.com/recoverindexapi/GetExpressInfoV2?sub_id=1859390&type=1", {...}); 查不到物流轨迹, 排查原因 返回结果: {... "data": { "waybillNo": "", "company": "", "routeList": [], ... }} 处于应该有物流轨迹的状态, 这个是测试环境的, 你可以直接查库分析 上面是提问的内容，llm能够通过查询找到的信息，就不要让human in loop，目前回复：... 在此之前需要你补充两点：1. 你说"处于应该有物流轨迹的状态"，是依据订单/售后单的哪个状态字段或业务节点判断的？... 2. type=1 在这个接口里对应的是哪种业务单据...

## 已采用理解

- 用户已经提供测试环境接口、参数、返回体和授权“可以直接查库分析”。
- `sub_id`、`type`、接口路径、返回为空这些都是明确排查锚点。
- `type=1` 的业务语义、当前单据状态、运单号是否落库、接口查询条件是否过滤，均应优先通过代码和测试库查询确认。
- 只有缺少权限、工具不可达、查询失败、或者涉及生产数据且无法直连生产时，才触发 Human Loop。

## 验收样本

- 同类 fetch/curl/URL 问题已给测试环境和参数时，`missing_info` 不应要求用户补充接口地址、参数、状态字段或 type 语义。
- 助手应先查接口入口、参数映射、数据库记录和返回字段，而不是先问用户。
