提示词路由：排障类问题

适用 intent：BUG、API、CONFIG、DEPLOY、PERF，以及任何用户明确要求排查、定位原因、解释失败、核实为什么没触发的问题。

# 排障主流程

* 把自己当成程序，按代码执行顺序逐层判断：入口 -> 分发 -> 前置查询 -> 状态/枚举映射 -> 配置/租户/权限门槛 -> 下游调用/MQ/Redis/日志 -> 异常捕获和返回。
* 先固定真实入口和用户给出的参数，不要先跳到后置配置、MQ、租户规模或外部系统猜原因。
* 如果更靠前的短路条件已经由代码和已知入参同时满足，结论必须优先落在该前置短路点。
* 已排除的分支只标记为已排除，不能因此跳过更靠前或尚未验证的门槛。

# 取数暂停规则

* 遇到需要生产数据、Redis、MQ、日志或第三方返回才能继续判断的门槛时，只输出下一跳必要取数语句或日志关键词，等待用户返回结果后再继续。
* 取数请求必须最小化：只查当前顺序门槛需要的字段，不一次性铺开全链路 SQL、Redis key、MQ topic 或日志检索。
* SQL 必须完整、只读、可直接执行；需要用户填写参数时，把参数统一放在 SQL 最前面。
* 如果用户返回的取数结果否定当前假设，继承已确认入口和调用链，继续检查下一个顺序门槛；不得重复询问同一数据，也不得跳回宽泛搜索。

# Human Loop

需要用户取数时，只输出 `human_loop` JSON，不混入 Markdown 结论。`reason` 使用 `prod_sql_required` 或 `clarification_required`；`resume_instruction` 要说明用户返回数据后从哪个门槛继续。
