# 自动核实最短持续时间与有界退出规范

Last Updated: 2026-07-29

## Problem Statement

当最终回复评审认为现有证据仍不足，并返回 `source=unresolved`、`action=continue` 时，当前处理流程会立即结束工具调用并发送“已自动继续核实，但本轮仍未获得足够完整的直接证据。”这与文案表达的“继续核实”不一致，也使用户在 Agent 尚有机会补充直接证据时过早收到兜底回复。

目标行为是：从每次用户提问进入 Agent 处理时开始一个固定三分钟窗口。在窗口内出现证据不足判定时，当前任务必须继续调用工具核实；窗口不会因后续判定或续查轮次而重置。严格超过三分钟后，只有再次出现同一种证据不足判定，才允许停止查询并发送现有兜底回复。

续查必须有界且可证明有进展。每一轮续查都要取得至少一个此前未使用相同调用签名的证据工具结果；没有新证据时只允许一次定向纠偏，纠偏仍无进展则立即以明确的工具无进展原因退出。整项任务从同一提问时间起达到八分钟时必须停止，为现有九分钟流式安全期限保留余量。

## Solution

为一次用户提问建立任务级自动核实编排。编排持有不可变的任务开始时间、累计证据、已使用的证据工具调用签名、剩余证据缺口、是否已经执行过无进展纠偏，以及现有的全局工具保护状态。每轮由 Agent 工具执行、最终回复评审和退出判定组成。

状态迁移如下：

| 当前结果或条件 | 时间条件 | 进展条件 | 行为 |
| --- | --- | --- | --- |
| 评审通过，可形成最终结论 | 任意 | 任意 | 立即发送结论并结束任务 |
| Human Loop | 任意 | 任意 | 沿现有 Human Loop 路径结束 |
| 真实模型错误 | 任意 | 任意 | 沿现有错误路径结束 |
| 工具错误或全局工具保护上限 | 任意 | 任意 | 沿现有工具保护路径结束 |
| 流式回复已过期 | 任意 | 任意 | 沿现有流式过期路径结束 |
| 达到八分钟硬上限 | `elapsed >= 480000ms` | 任意 | 停止查询并发送现有证据不足兜底回复 |
| 证据不足并要求继续 | `elapsed <= 180000ms` | 本轮有新证据 | 保留任务状态，开始下一轮工具核实 |
| 证据不足并要求继续 | `elapsed <= 180000ms` | 本轮无新证据，尚未纠偏 | 注入剩余证据缺口和已使用调用，强制纠偏一轮 |
| 纠偏轮仍无新证据 | 未达硬上限 | 无新证据 | 立即以明确的工具无进展原因结束，不发送证据不足兜底 |
| 证据不足并要求继续 | `elapsed > 180000ms` | 任意 | 停止查询并发送一次现有证据不足兜底回复 |

三分钟边界采用严格“超过”语义：恰好经过 180,000 毫秒时仍在保护窗口内；下一次评审只有在经过时间大于 180,000 毫秒时才允许兜底退出。八分钟边界采用“达到”语义：经过时间大于或等于 480,000 毫秒即触发硬上限。

新证据以证据工具调用签名判定。签名由规范化工具名和稳定排序后的参数组成。TodoList 更新不属于证据；与任务中任何既有证据调用具有完全相同签名的结果也不属于新证据。重复调用仍受现有全局限制，并可按现有机制执行，但不能满足续查进展条件。

## User Stories

### 1. 三分钟内自动续查

作为正在等待代码或业务事实核实的用户，我希望证据不足发生在提问后的三分钟内时 Agent 继续使用工具，以便在仍有查询机会时获得完整结论，而不是立即看到兜底回复。

验收条件：

- 给定一次任务尚未超过 180,000 毫秒；
- 当最终评审返回 `unresolved + continue`；
- 则不发送最终兜底回复，不结束流式卡片，并进入下一轮 Agent 工具执行。

### 2. 固定计时起点

作为用户，我希望三分钟从本次提问开始处理时计算，以便每次提问都有独立、可预测的核实窗口。

验收条件：

- 任务开始时间只在本次用户提问进入 Agent 处理时记录一次；
- 后续证据不足判定、Agent 续查、工具回调和最终评审均不修改该时间；
- “继续”消息若属于当前仍活跃任务，则沿用当前任务及其开始时间；
- 新问题或替换任务创建新的开始时间。

### 3. 严格三分钟边界

作为用户，我希望“超过三分钟”按字面执行，以避免临界点被提前退出。

验收条件：

- 经过 179,999 毫秒时，`unresolved + continue` 继续核实；
- 经过恰好 180,000 毫秒时，`unresolved + continue` 仍继续核实；
- 经过 180,001 毫秒或更多时，下一次 `unresolved + continue` 才触发兜底退出。

### 4. 三分钟后按下一次判定退出

作为用户，我希望 Agent 在超过三分钟后仍以实际评审结果决定是否结束，以免仅因时钟越界打断正在形成的有效结论。

验收条件：

- 时间越过三分钟本身不主动发送回复；
- 超过三分钟后若评审通过，立即发送正常结论；
- 超过三分钟后若再次得到 `unresolved + continue`，停止查询并仅发送一次现有兜底回复。

### 5. 有效结论立即交付

作为用户，我希望完整结论一经评审通过即可收到，以免为了满足最短核实窗口而被无意义延迟。

验收条件：

- 在任意续查轮次，评审结果已经可交付时立即结束编排；
- 无需等待三分钟；
- 最终内容沿现有正常回复路径发送。

### 6. 每轮必须新增证据

作为维护者，我希望续查轮次具有可观测进展，以防 Agent 用无效操作或重复查询空转。

验收条件：

- 每个续查轮次记录其开始前已经见过的证据调用签名；
- 轮次结束后至少新增一个此前未见的证据工具调用结果，才视为有进展；
- TodoList 更新不能计为证据；
- 完全相同的工具名和规范化参数不能计为新证据，即使该调用再次返回结果。

### 7. 一次定向纠偏

作为维护者，我希望首次无进展时给 Agent 一次明确纠正机会，以处理可以通过调整查询范围解决的问题。

验收条件：

- 首次无新证据的续查轮次不立即进入证据不足兜底；
- 下一轮提示必须携带尚未解决的证据缺口和已经使用的工具调用参数；
- 提示明确要求改用新的有效查询；
- 纠偏机会对当前无进展事件只执行一次。

### 8. 无进展明确退出

作为用户，我希望 Agent 无法产生新查询时如实说明，以免它伪装成仍在核实或无意义等待到三分钟。

验收条件：

- 定向纠偏后仍没有新证据时立即停止；
- 回复明确说明无法产生新的有效工具查询；
- 不发送证据不足兜底文案；
- 不等待三分钟或八分钟上限。

### 9. 重复调用保护保持有效

作为维护者，我希望新增循环不削弱现有工具调用保护，以防跨轮次重复调用绕过全局限制。

验收条件：

- 同一任务的工具结果数、重复调用数和工具错误数在续查轮次之间持续累计；
- 现有全局阈值和退出语义保持不变；
- 仅包含重复调用的轮次按无新证据处理；
- 达到现有保护上限时沿真实工具保护路径退出。

### 10. 八分钟硬上限

作为用户，我希望异常情况下任务仍能确定结束，以避免企业微信流式回复临近安全过期。

验收条件：

- 硬上限与三分钟窗口使用同一个任务开始时间；
- 经过时间达到 480,000 毫秒时停止继续查询；
- 发送一次现有证据不足兜底回复并完成当前流式卡片；
- 不因续查或纠偏刷新硬上限。

### 11. 特殊退出不被改写

作为维护者，我希望真实错误和人工确认保持原有语义，以便运维和用户看到准确原因。

验收条件：

- Human Loop、真实模型错误、工具错误上限和流式过期均立即退出；
- 这些结果不等待三分钟；
- 这些结果不转换成证据不足兜底；
- 原有可操作错误信息继续传递给用户或日志。

### 12. 会话隔离

作为多个私聊或群聊中的用户，我希望自己的核实计时和进展不受其他会话影响。

验收条件：

- 任务仍按现有会话键隔离；
- 私聊用户之间互不共享计时或证据；
- 不同群聊之间互不共享计时或证据；
- 同一群聊的不同发送者之间互不共享计时或证据。

### 13. 流式生命周期完整

作为企业微信用户，我希望续查期间卡片保持活跃，并在真实终态只结束一次。

验收条件：

- 继续核实时保持当前任务和流式心跳；
- 中间的证据不足判定不把流式卡片标记为最终态；
- 正常结论、兜底、无进展、Human Loop 或真实错误进入终态时，按各自现有路径正确结束；
- 同一任务不会重复发送最终兜底。

## Implementation Decisions

- 引入一个任务级自动核实编排边界，负责按轮次协调 Agent 工具执行、最终回复评审、进展判定和终态交付。
- 编排使用依赖注入的时间来源、Agent 轮次执行器和最终评审器，使核心状态迁移可以脱离网络与企业微信运行时确定性测试。
- 任务开始时间为不可变值，由本次用户提问进入 Agent 处理时传入；所有窗口与硬上限均计算 `now - startedAt`。
- 三分钟保护窗口只消费 `source=unresolved` 且 `action=continue` 的评审结果。其他评审结果和运行时保护结果保持现有优先级与语义。
- 八分钟硬上限在开始新一轮昂贵查询前和处理轮次结果后检查，避免越过上限后继续启动无意义工具调用。
- 证据工具调用签名使用稳定参数规范化。TodoList 工具被排除，任务内已经出现过的签名不再视为新证据。
- 工具进展保护状态提升到整个任务生命周期复用，确保跨轮次结果数、重复次数和错误次数不会重置。
- 每轮保留累计候选答案、工具证据、证据缺口与调用签名；下一轮续查基于这些上下文继续，而非从空白请求重新开始。
- 无新证据纠偏是一种显式的一次性状态。纠偏输入包括未解决证据缺口与已使用调用，纠偏失败产生专用工具无进展终态。
- 当前兜底回复内容保持不变；本需求只改变它被允许发送的时机。
- 流式回复在自动续查期间保持非最终状态，仅在一个明确终态被选定后结束一次。
- 不新增跨会话全局计时器或共享进度状态；每个活跃任务独立持有编排状态。

## Testing Decisions

采用一个新的、可注入依赖的自动核实编排函数作为最高层主测试入口。测试以假的 Agent 工具轮次、假的最终评审器和可控时间验证完整状态迁移，不启动真实企业微信连接、WebSocket、模型或 MCP 服务。

主测试入口至少覆盖：

- 首次 `unresolved + continue` 发生在三分钟内时确实调用下一轮，而非只返回“应继续”的策略值；
- 多次三分钟内续查不刷新开始时间；
- 179,999、180,000 和 180,001 毫秒的严格边界；
- 超过三分钟后以“下一次证据不足判定”退出；
- 三分钟后出现可交付结论仍立即返回正常答案；
- 任务在 480,000 毫秒达到硬上限；
- 每轮出现新的唯一证据调用时允许继续；
- TodoList-only、重复签名-only 和完全无工具结果均不满足进展条件；
- 首次无进展触发一次定向纠偏，第二次无进展进入专用工具无进展终态；
- 全局重复调用和工具错误保护跨轮次保持累计；
- Human Loop、真实模型错误和运行时保护退出不被转成证据不足兜底；
- 两个不同会话任务的开始时间、签名集和纠偏状态互不影响。

现有最终回复交付测试继续作为窄回归入口，验证兜底文案保持不变，以及正常结论、真实模型错误和 Human Loop 的内容分流。另以最小集成测试验证编排终态只结束一次流式回复；真实外部服务留给人工或环境集成验证。

测试采用确定性时间，不使用真实等待三分钟或八分钟。先提交能证明当前行为会过早兜底的失败测试，再实施最小变更使其通过，并运行相关回归与 TypeScript 编译检查。

## Out of Scope

- 改变最终回复评审模型判断“证据充分”的标准。
- 修改现有证据不足兜底回复文案。
- 修改企业微信流式安全期限、Human Loop 期限或会话清理期限。
- 为其他类型的最终评审结果增加自动重试。
- 引入持久化任务队列、分布式锁或跨进程续查恢复。
- 重做工具注册、工具协议或业务查询实现。
- 与本需求无关的文件重构、格式化、暂存、提交、推送或部署。

## Further Notes

- “三分钟”是发送证据不足兜底前的固定保护窗口，不是要求正常答案至少等待三分钟。
- “再次触发”指超过三分钟后，最终回复评审再次返回 `unresolved + continue`；单纯经过时间阈值不构成退出事件。
- 会话键只提供隔离；计时对象是每一次用户提问对应的活跃任务。
- 本变更属于可逆的运行时编排调整，无需新增架构决策记录。
- 项目未配置可用的问题跟踪器发布入口，本规范以仓库内文档作为后续 Tickets、TDD、实现和评审阶段的正式输入。
